## 1. Por que esta fase importa mais do que parece

O roadmap descreve o F0.2 como "build distribuível", mas o valor real é outro: **é o marco que prova cadência de entrega.** O diagnóstico do projeto apontou 5 commits em 7 meses como o sinal mais preocupante — não a arquitetura. Um `.exe` na mão de 3 pessoas fecha o primeiro ciclo completo de "construir → entregar → ouvir".

É também a primeira vez que o jogo sai do Editor. Tudo que hoje funciona porque *o Editor compensa* vai aparecer aqui.

## 3. Estado verificado

### Build settings — 6 cenas, todas existem

`MainMenu`, `Loading`, `TowerPicks`, `TowerRun`, `Characters`, **`Sandbox` (enabled)**.

O Sandbox é ferramenta de teste de unidades e está **alcançável pelo menu principal**. Numa build pública é uma feature acidental: ganha QA, suporte e expectativa para sempre.

### CanvasScaler — duas cenas não escalam de jeito nenhum

| Cena | Modo | Referência | Match |
|---|---|---|---|
| **MainMenu** | **`ConstantPixelSize`** | 800×600 | 0,00 |
| **Loading** | **`ConstantPixelSize`** | 800×600 | 0,00 |
| TowerPicks | `ScaleWithScreenSize` | 1920×1080 | 0,50 |
| TowerRun | `ScaleWithScreenSize` | 1920×1080 | 0,50 |
| **Characters** | `ScaleWithScreenSize` | 1920×1080 | **0,00** |
| Sandbox | `ScaleWithScreenSize` | 1920×1080 | 0,50 |

`ConstantPixelSize` significa que a UI **não escala** — em 1080p a interface desenhada para 800×600 aparece no tamanho errado. É o defeito visual mais provável de aparecer na primeira build. `Characters` com `match=0` escala só pela largura e quebra em telas mais altas.

### Logging — 167 call sites, nenhum filtro no player

`DebugManager` carrega a config por `Resources.Load<DebugConfig>("DebugConfig")` ([DebugManager.cs:19](../../Assets/Scripts/Utils/Debug/DebugManager.cs#L19)), mas o asset está em **`Assets/Scripts/Utils/Debug/DebugConfig.asset`** — fora de qualquer pasta `Resources`. O load retorna `null` e o logging cai em não-filtrado.

Mesmo problema em `Assets/Scripts/Combat/Preparation/PreparationConfig.asset`.

> **Violação de convenção:** as heurísticas dizem `Assets/Scripts/` = código, `Assets/Data/` = asset. Estes dois `.asset` estão no lugar errado, e é justamente por isso que o `Resources.Load` falha.

### Player settings

| Campo | Valor | Observação |
|---|---|---|
| `fullScreenMode` | `FullScreenWindow` | ok como padrão |
| `defaultScreenWidth/Height` | 1920×1080 | ok |
| **`resizableWindow`** | **`False`** | jogador de PC espera redimensionar |
| **`runInBackground`** | **`True`** | com `targetFrameRate` ausente, o jogo renderiza sem limite em segundo plano |
| `scriptingBackend` | `Mono2x` | — |
| **`managedStrippingLevel`** | **`Disabled`** | ⚠️ ver risco abaixo |

> ⚠️ **Não habilite managed stripping nesta fase.** O projeto depende de **reflexão por convenção**: `CharacterData.GetBaseStat(StatType.X)` resolve o campo `baseX` por nome, e o markup de ability-text `{v:field}` também lê por reflexão. Ambos **retornam 0 em silêncio** se o membro for removido. Habilitar stripping sem um `link.xml` quebraria stats e descrições sem nenhum erro. Fica `Disabled`; o custo é tamanho de build, que não importa neste alvo.

## 4. Decisões técnicas

### D1 · O que fazer com o Sandbox

| | **A · Remover da build** | **B · Manter atrás de define** |
|---|---|---|
| Como | Tirar de `EditorBuildSettings` e esconder a entrada no menu | `#if DEVELOPMENT_BUILD` no botão; cena só na build de dev |
| Custo | Minutos | Exige duas configurações de build |
| Risco | Nenhum | Divergência entre o que você testa e o que eles jogam |

**Recomendação: A.** O Sandbox é ferramenta sua; você roda no Editor. Duas configurações de build num projeto sem CI é complexidade que não se paga agora.

### D2 · Como o `DebugConfig` chega ao runtime

O projeto já resolveu esse problema uma vez: configs globais passam por **`GameConfig.Active`**, com o único agregador em `Data/Resources/GameConfig.asset` (decisão do F0.1). O `Resources.Load` direto do `DebugConfig` é o padrão antigo que sobrou.

**Recomendação: dobrar `DebugConfig` e `PreparationConfig` no `GameConfig`**, mover os `.asset` para `Assets/Data/Config/`, e apagar os dois `Resources.Load` avulsos. Resolve o bug e a violação de convenção de uma vez, sem introduzir uma segunda pasta `Resources`.

### D3 · Escopo da tela de opções

Áudio não existe (F4.6) e idioma está fora do beta. Sobra o essencial de um jogo de PC:

- Resolução (lista das suportadas) e modo de tela (tela cheia / janela sem borda / janela)
- **Sair do jogo**
- Persistência das escolhas

Persistir onde: `PlayerPrefs` resolve, mas o F5.1 traz Steam Auto-Cloud sobre `persistentDataPath`. **Recomendo já gravar num JSON em `persistentDataPath`**, no mesmo molde do `BuildStore`, com `schemaVersion` — assim o Auto-Cloud pega de graça depois.

### D4 · `runInBackground` e limite de framerate

Hoje `True` sem `targetFrameRate`: alt-tab mantém o jogo renderizando a todo vapor. Num jogo que o F3.3 quer "deixar rodando por horas", isso é desenho, não detalhe.

**Recomendação para esta fase:** `Application.targetFrameRate = 60` no boot e manter `runInBackground = True` (o PVP do F5 vai precisar dele). O modo de farm ganha o próprio controle no F3.3.

### D5 · Script de build

Um `MenuItem` de editor que chama `BuildPipeline.BuildPlayer` com cenas, alvo e caminho fixos, versionando o `.exe` por `bundleVersion`. Sem CI nesta fase — `.github` entra quando houver testes para rodar (F0.4).

## 5. Ordem de execução

| # | Passo | Prova |
|---|---|---|
| **1** | Mover `DebugConfig.asset` e `PreparationConfig.asset` para `Assets/Data/Config/`; dobrá-los no `GameConfig`; remover os `Resources.Load` avulsos | Log filtrado por categoria funciona no Editor; `PreparationConfig` deixa de cair no default |
| **2** | Padronizar `CanvasScaler` nas 6 cenas: `ScaleWithScreenSize`, 1920×1080, match 0,5 | Cada cena legível em 1920×1080, 1280×720 e 2560×1440 |
| **3** | Tirar o Sandbox de `EditorBuildSettings` e esconder a entrada no `MainMenuController` | Build não contém a cena; menu não a oferece |
| **4** | Tela de opções: resolução, modo de tela, sair; persistida em `persistentDataPath` com `schemaVersion` | Trocar resolução, fechar, reabrir e a escolha persiste |
| **5** | `Application.Quit` no menu e um `Esc` que volta/abre pausa. **Confirmar que fecha o processo** | O `.exe` fecha sem Gerenciador de Tarefas |
| **6** | `targetFrameRate = 60` no boot | Uso de GPU cai em segundo plano |
| **7** | Script de build (`Tools ▸ DropInHeroes ▸ Build Windows`) | `.exe` gerado por um clique, nomeado com a versão |
| **8** | **Passada de primeira impressão** — jogar do `.exe` como se fosse a primeira vez, anotando tudo que confunde | Lista de defeitos priorizada |
| **9** | Corrigir o que a passada 8 achou, dentro do escopo | — |
| **10** ⚠️ | **Entregar a 3 pessoas de fora**, com um canal de retorno combinado | Relatos coletados |

> O passo 8 é o mais valioso e o mais fácil de pular. Jogar a partir do `.exe`, em outra máquina se possível, revela o que o Editor esconde: cena faltando no build, asset em `Resources` que não existe, shader não incluído, resolução quebrada.

## 8. Riscos de regressão

| Risco | Prob. | Detecção | Mitigação |
|---|---|---|---|
| **Trocar o CanvasScaler quebra o layout de MainMenu/Loading** | **Alta** | Passo 2, visualmente | É re-layout esperado, não bug. Fazer cena por cena, com captura antes/depois |
| **Asset que só existe no Editor some na build** | Média | Passo 8, no `.exe` | Testar sempre a partir do `.exe`, nunca só no Editor |
| Dobrar configs no `GameConfig` quebra o fallback silencioso de que algo dependia | Média | Passo 1, no Editor | Os fallbacks atuais são acidentais; o comportamento correto é o config carregar |
| **Habilitar stripping quebra a reflexão** | Baixa | Stats zerados e descrições vazias, **sem erro** | Manter `Disabled` nesta fase (§3) |
| Esconder o Sandbox deixa referência quebrada na cena | Baixa | Console ao abrir `MainMenu` | Remover o botão, não só desativar |
